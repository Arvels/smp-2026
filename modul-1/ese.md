# JSON як предметна мова для обміну та зберігання структурованих даних

## Вступ

У сучасних застосунках інформація постійно переходить між різними компонентами: браузером і сервером, мобільним застосунком і хмарною платформою, програмою та її файлом налаштувань. Дані мають залишатися зрозумілими незалежно від того, якою мовою програмування написана кожна частина системи. Для цього потрібна спільна форма запису: достатньо проста для читання людиною і водночас однозначна для автоматичного оброблення. Одним із найпоширеніших рішень є **JSON (JavaScript Object Notation)**.

JSON часто називають форматом даних, але в межах теми предметних мов його доречно розглядати як невелику декларативну мову для опису структури значень. Вона не містить команд на зразок циклів або функцій: автор описує **які саме дані існують**, а не **як програма повинна їх обчислювати**. Завдяки обмеженому набору конструкцій JSON використовується там, де потрібен передбачуваний обмін інформацією.

У цьому есе розглянуто практичне завдання, яке розв'язує JSON, його користувачів, мінімальний приклад, вдалі та невдалі синтаксичні рішення, а також альтернативу без спільного формату. Як наскрізний приклад використано власний навчальний застосунок **GreekWordsBot** — чат-бот для вивчення грецьких слів.

## 1. Яку задачу розв'язує JSON і хто його використовує

Головна задача JSON — **представити структуровані дані у вигляді тексту**, щоб одна програма могла їх зберегти або передати, а інша — прочитати без здогадів щодо структури. Наприклад, сервер інтернет-магазину надсилає клієнтові інформацію про товар, його ціну та доступність. Або застосунок читає файл із параметрами запуску: мову інтерфейсу, ліміт запитів, перелік доступних функцій. В обох випадках потрібно передати не довільний текст, а чітко організовані значення.

JSON пропонує кілька базових типів: **рядок**, **число**, **логічне значення**, **`null`**, **масив** і **об'єкт**. Об'єкт зберігає пари «ключ — значення», а масив — упорядкований список значень. Цього достатньо, щоб описати багато реальних структур: користувача з контактами, кошик із товарами, налаштування застосунку або відповідь вебсервісу.

Кінцевий користувач JSON не завжди бачить його безпосередньо. Звичайний відвідувач сайту натискає кнопку й отримує результат на екрані, хоча «за лаштунками» браузер може отримати JSON від сервера. Натомість **розробник**, **тестувальник**, **інженер з автоматизації** або **адміністратор системи** працює з JSON свідомо: створює файли конфігурації, перевіряє відповіді API, шукає помилки в значеннях. Для цих людей важливо, щоб запис був компактним, а правила його читання — стабільними.

У GreekWordsBot JSON потрібен для відокремлення налаштувань від програмного коду. Якщо користувач хоче збільшити щоденну норму слів із 15 до 20, не обов'язково переписувати логіку бота. Достатньо змінити значення параметра `daily_goal` у файлі конфігурації. Таке відокремлення робить застосунок простішим для супроводу: поведінка визначається програмою, а конкретні значення — конфігурацією.

Водночас слід розрізняти два рівні користувачів. **Безпосередній користувач мови JSON** — людина або програма, яка читає чи створює структурований текст. **Кінцевий користувач GreekWordsBot** — учень, який вивчає грецьку мову; він може взагалі не знати про JSON, проте його параметри впливають на щоденні заняття.

## 2. Мінімальний робочий приклад і його пояснення

Найпростіший конфігураційний файл може містити лише назву програми, її версію, щоденну ціль і стан сповіщень. Для реального застосунку зручно також мати список тем і вкладений блок налаштувань навчання:

```json
{
  "app_name": "GreekWordsBot",
  "version": "1.10",
  "daily_goal": 20,
  "notifications_enabled": true,
  "topics": ["Вітання", "Подорожі", "Покупки"],
  "learning": {
    "target_language": "el",
    "repeat_mistakes": true
  }
}
```

Зовнішні фігурні дужки позначають об'єкт налаштувань. Кожен параметр має назву в подвійних лапках і значення після двокрапки. Коми відділяють пари одна від одної, але після останньої пари кома не ставиться. Поле `app_name` — рядок, `daily_goal` — ціле число, `notifications_enabled` — логічне значення. У `topics` міститься масив із трьох тем, а `learning` є вкладеним об'єктом. Отже, один текстовий документ передає прості й складені дані без додаткових умовних позначень.

Особливу увагу варто приділити полю `version`. Запис **`"1.10"` у лапках** означає саме номер версії, тобто рядок. Без лапок `1.10` трактувався б як число; після читання програмою воно могло б відображатися як `1.1`. Для версії ці записи не тотожні: версія 1.10 не обов'язково є версією 1.1. Це приклад того, як правильний вибір типу захищає значення від непомітного спотворення.

JSON сам по собі нічого не запускає. Щоб використати файл, його потрібно прочитати програмою. Наприклад, стандартний модуль Python `json` перетворює текст на словник:

```python
import json

with open("config.json", encoding="utf-8") as file:
    config = json.load(file)

print(config["app_name"])
print(config["daily_goal"])
print(config["learning"]["target_language"])
```

Якщо зберегти попередній JSON у файлі `config.json` і запустити Python-код із тієї самої теки, результат буде таким:

```text
GreekWordsBot
20
el
```

Модуль `json` виконує розбір тексту, а Python надає доступ до значень за ключами. Таким чином, JSON описує дані, а Python реалізує поведінку застосунку. Це розділення ролей є важливою перевагою: той самий JSON може прочитати не лише Python, а й застосунок іншою мовою програмування.

Однак файл, який синтаксично правильно розібрався, не обов'язково містить правильні для конкретної програми параметри. Наприклад, `"daily_goal": -5` є допустимим JSON, але від'ємна кількість слів не має сенсу для бота. Тому після читання конфігурації програма повинна перевірити **значення та бізнес-правила**, а не тільки синтаксис.

## 3. Вдале рішення у синтаксисі JSON

На мою думку, найбільш вдалою рисою JSON є **малий, однозначний набір конструкцій**. Для всіх основних випадків достатньо об'єктів, масивів і простих типів. Розробнику не потрібно вивчати великий набір команд, спеціальних ключових слів чи складні правила виконання. За фігурними дужками легко впізнати об'єкт; за квадратними — масив; за подвійними лапками — рядок.

Особливо корисне поєднання **вкладених об'єктів і масивів**. У GreekWordsBot теми навчання природно записати як масив `topics`, а параметри режиму навчання — як об'єкт `learning`. Це краще, ніж вигадувати окремі назви `topic1`, `topic2`, `topic3` або змішувати всі параметри в один плоский список. Такі структури відповідають тому, як люди зазвичай уявляють предметну область: «застосунок має кілька тем», «режим навчання має кілька налаштувань».

Інше вдале рішення — чітке розрізнення типів. Рядок `"20"` і число `20` мають різний зміст, як і `true` та `"true"`. Програма може одразу працювати з числом як із числом, не виконуючи додаткового перетворення з тексту. Водночас програміст відповідає за те, щоб обрати належний тип, а не покладатися на автоматичні здогади парсера.

Однозначність синтаксису також допомагає автоматичним інструментам. Редактори можуть підсвічувати помилки, а парсери — повідомляти, коли пропущено лапки чи кому. Це не гарантує правильність усієї конфігурації, проте прибирає частину неоднозначностей, які виникали б у довільному текстовому форматі.

## 4. Невдале рішення у синтаксисі JSON

Найбільш незручним обмеженням JSON для ручного редагування я вважаю **відсутність коментарів**. У стандартному JSON не можна написати пояснювальний рядок, що починається з `//` або `#`. Це особливо помітно в конфігураційних файлах: навіть якщо назва параметра зрозуміла, не завжди очевидно, чому обрано певне значення.

Наприклад, адміністратор може збільшити норму слів до 20, бо учні попросили інтенсивніший режим. У YAML чи TOML причину можна було б залишити поруч із параметром як коментар. У JSON запис нижче **неправильний**:

```javascript
{
  "daily_goal": 20 // Збільшено після відгуків учнів
}
```

Це лише ілюстрація забороненого синтаксису: справжній JSON-парсер відхилить такий текст через коментар. Доводиться переносити пояснення в README, окрему документацію або історію Git. Можна додати поле на кшталт `"note"`, але тоді пояснення стає частиною даних, а не коментарем, і програма має вирішувати, що з ним робити.

Ще одна незручність — **обов'язкові подвійні лапки навколо ключів і рядків**, а також заборона коми після останнього елемента. Такі правила роблять формат простим для машин, але збільшують кількість дрібних помилок під час ручного редагування. Наприклад, додавши новий параметр, легко забути кому між двома рядками. Парсер виявить помилку, проте користувачеві однаково доведеться її виправити.

Ці недоліки не означають, що JSON поганий формат. Вони показують його пріоритет: **стандартизований обмін даними важливіший за зручність написання великих конфігурацій вручну**. Для компактних відповідей веб-API це виправдано; для файлу, який часто змінюють люди й активно коментують, іноді краще підходить TOML або YAML.

## 5. Як це робилося б без JSON і чому було б гірше

Без JSON розробник міг би зберігати налаштування у звичайному текстовому файлі, наприклад так:

```text
GreekWordsBot
1.10
20
true
Вітання,Подорожі,Покупки
el,true
```

На перший погляд, такий варіант коротший. Але тепер потрібно домовитися, що перший рядок — назва, другий — версія, третій — ціль, а значення через кому є списком. Якщо поміняти рядки місцями, програма може прочитати неправильне значення без очевидної підказки. Якщо назва теми сама міститиме кому, доведеться вигадувати правило екранування. Для нового параметра потрібно змінити і спосіб запису, і власний парсер.

Другий варіант — прописати налаштування безпосередньо в програмі:

```python
daily_goal = 20
notifications_enabled = True
```

Це зручно для короткого навчального прикладу, проте незручно для справжнього застосунку. Щоб змінити параметри, доведеться редагувати вихідний код. Людина, відповідальна лише за налаштування, отримує доступ до програмної логіки й може випадково змінити не те. Налаштування також складніше використовувати повторно в застосунку, написаному іншою мовою.

Третій варіант — передавати кожне значення окремо через параметри командного рядка або змінні середовища. Це корисний підхід для деяких систем, особливо для секретів і параметрів розгортання. Проте складні списки та вкладені об'єкти в такому вигляді менш зручні; крім того, значення змінних середовища зазвичай передаються як текст, тож їхні типи треба перетворювати й перевіряти.

JSON розв'язує головну проблему цих способів: він задає **спільну структуру**, яку розуміють багато мов програмування. Один файл можна зберігати в Git, перевіряти під час тестування та використовувати для обміну між різними частинами системи. Замість написання власного розбирача розробник користується перевіреною бібліотекою. Це зменшує кількість власного коду й полегшує підтримку проєкту.

Разом із тим JSON не слід вважати універсальною заміною всіх способів конфігурації. Паролі й токени не варто зберігати у відкритому файлі, який потрапляє до репозиторію. Так само великий набір параметрів, що потребують детальних пояснень, може бути зручнішим у форматі з підтримкою коментарів. Вибір інструмента залежить від того, хто створює дані, хто їх читає і як часто вони змінюються.

## Висновок

JSON — це компактна декларативна предметна мова для представлення структурованих даних. Вона допомагає різним програмам узгоджено обмінюватися значеннями й дозволяє відокремити налаштування застосунку від його програмного коду. На прикладі GreekWordsBot видно, як кілька простих типів, масив і вкладений об'єкт описують реальну конфігурацію, яку Python може прочитати без власного парсера.

Найвдалішим рішенням JSON я вважаю передбачувану структуру з невеликої кількості конструкцій, а найменш вдалим для ручних конфігурацій — заборону коментарів. Без JSON довелося б створювати власні правила для тексту або жорстко прив'язувати налаштування до коду, що збільшило б кількість помилок і ускладнило підтримку. Тому для обміну даними між програмами я обрав би JSON, а для великих конфігурацій, які регулярно редагують люди, окремо розглянув би TOML.
